# Deploy WorkSync with Render and Supabase

This repository is a monorepo. The root `render.yaml` defines a Render Node web service for the API and a Render static site for the Vite frontend. Supabase supplies the PostgreSQL database; the Blueprint intentionally does not create a second database.

## 1. Prepare Supabase PostgreSQL

1. Create a Supabase project and set a strong database password.
2. In the Supabase dashboard, open **Connect** and copy the connection URIs. `DATABASE_URL` is used by the running API; use a direct connection when reachable, or the session pooler on port `5432` for IPv4. If you use Supavisor transaction mode on port `6543` for runtime traffic, include `pgbouncer=true`. `DIRECT_URL` is used by Prisma CLI migrations; use the direct connection when Render can reach it, or Supavisor session mode on port `5432` when you need IPv4. Use the URI Supabase provides; do not construct the pooler hostname yourself. Replace password placeholders and percent-encode reserved characters in passwords.
3. Keep both URIs private. Enter them as `DATABASE_URL` and `DIRECT_URL` in Render during Blueprint setup.

Supabase documents the [Prisma connection setup](https://supabase.com/docs/guides/database/prisma) and its [connection modes](https://supabase.com/docs/guides/database/connecting-to-postgres). Prisma uses `directUrl` for CLI operations such as migrations while Prisma Client uses `url` at runtime.

## 2. Add required production services

Production startup is configured to fail unless durable object storage and SMTP are provided:

- Create an S3-compatible bucket, such as Cloudflare R2 or AWS S3. Enter its bucket, region, endpoint, access key ID, and secret access key in the Render API service settings. For AWS S3, use the AWS region and leave `STORAGE_ENDPOINT` unset; for R2, use region `auto` and the R2 S3 endpoint.
- Configure an SMTP relay and verified sender address. Enter the SMTP host, sender, and credentials in Render. If the relay does not require authentication, leave both SMTP user and password empty.

Never add these credentials to the repository or frontend. Vite variables are shipped in public browser assets; only `VITE_API_URL` and `VITE_SOCKET_URL` belong in the frontend.

## 3. Create the Render services

1. Push this repository to GitHub.
2. In Render, choose **New → Blueprint** and select the repository. Render reads the root `render.yaml` and creates `worksync-api` and `worksync-frontend`.
3. When prompted for `sync: false` values, enter the Supabase `DATABASE_URL` and `DIRECT_URL`, SMTP values, and S3 storage values. `JWT_SECRET` is generated by Render.
4. The Blueprint links the frontend and API public URLs automatically. The frontend appends `/api/v1` to the API origin and uses that same origin for Socket.IO. The API uses the frontend URL for CORS.

The API Blueprint build command runs `prisma generate` and `prisma migrate deploy` from `worksync-backend`, using the project-local Prisma CLI. This makes deployments apply committed migrations to Supabase before the new API starts. Root-level `npm run db:deploy` is also available for running the migration command from the repository root when both `DATABASE_URL` and `DIRECT_URL` are configured.

## 4. Verify deployment

- Open `https://<api-service>.onrender.com/health`. A healthy response includes `"database":"ok"`.
- Open the frontend's Render URL and check browser developer tools for API or CORS errors.
- Confirm the API service's `CLIENT_URL` exactly matches the frontend origin, including `https://` and excluding a trailing path.

## Local commands

Run backend Prisma commands from the backend directory, or use these root shortcuts:

```powershell
npm run db:migrate
npm run db:deploy
```

The root command `npx prisma migrate dev` is not valid for this monorepo because Prisma is installed in `worksync-backend`, not at the repository root.
